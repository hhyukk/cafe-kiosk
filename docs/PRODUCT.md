## 1. 이 프로젝트는 무엇인가

**한 줄 정의**

> 한 대의 키오스크에서 낸 주문이 주방 화면에 흘러가고, 재고가 실제로 줄어들며,
> **마지막 한 잔을 두 손님이 동시에 누르면 정확히 한 명만 성공한다.**

마지막 절이 이 프로젝트의 존재 이유다. 카페 키오스크는 흔한 소재지만, 이 레포가 진짜로 다루려는 주제는 **재고 동시성 제어**다. 키오스크는 그 문제가 가장 자연스럽게 발생하는 무대로서 선택된 것이지, 그 자체가 목적이 아니다.

### 1-1. 정체성 진단 — 지금 이 레포는 두 개의 제품이 겹쳐 있다

전수 조사 결과, 코드 품질보다 먼저 해결해야 할 문제가 발견됐다.

| | 무엇을 말하고 있나 |
| --- | --- |
| **레포 이름 + 백엔드** | **매장 키오스크.** `OrderStatus`가 `CONFIRMED → IN_PROGRESS(제조중) → READY(준비완료) → COMPLETED`다. 이건 배송 흐름이 아니라 **카운터에서 음료를 내주는** 흐름이다. |
| **프론트엔드** | **원두 배송 쇼핑몰.** 주문할 때 **주소와 우편번호를 받는다**(`Order.address`, `Order.postcode`). 화면엔 *"당일 오후 2시 이후의 주문은 다음 날 배송을 시작합니다"*라는 문구까지 있다(`frontend/src/app/page.tsx:652`). |

이 분열은 미관상의 문제가 아니라, **기능들이 서로를 만나지 못하게 만들고 있다.**

- 백엔드는 주문 상태머신을 공들여 만들었는데(`Order` 엔티티 + `OrderTest` 8개 — 이 레포에서 가장 잘 설계된 부분이다), **주문 조회 응답에 `status`도 `orderId`도 없다**. 프론트가 주문 상태를 볼 방법이 아예 없다. 상태를 바꾸는 API는 있는데 상태를 읽는 경로가 없다.
- `Stock` 엔티티는 존재하는데 **`OrderService`가 `Stock`을 단 한 번도 참조하지 않는다**(grep 결과 0건). 그래서 **재고가 0이어도 무한히 주문된다.**
- `docker-compose.yml`에 Redis가 떠 있는데 **`build.gradle.kts`에 Redis 의존성이 없다.** 컨테이너만 돌고 코드는 안 쓴다.

### 1-2. 결론: **매장 키오스크로 확정한다.** 배송몰을 버린다.

근거는 셋이다.

1. **백엔드 상태머신이 이미 매장 모델이다.** 배송으로 방향을 틀면 이 레포에서 유일하게 잘 설계된 자산을 버리고 다시 짜야 한다.
2. **동시성 실습은 매장 모델에서만 긴장감이 생긴다.** "마지막 한 잔"은 매장에서 벌어지는 일이다. 배송몰은 재고를 미리 확보해두는 게 정상 운영이라, 억지로 경쟁 상황을 만들어야 한다.
3. **주소/우편번호는 부트캠프 팀 프로젝트(2025-12) 시절의 잔재다.** 개인 리팩터링기(2026-05~)에 쌓인 커밋 — PostgreSQL 전환, Testcontainers, 기능별 패키지, `Stock` 도메인, 주문 상태머신 — 은 **전부 매장 방향을 향하고 있다.** 프론트만 과거에 멈춰 있는 것이다.

### 1-3. 흩어진 단서들이 이미 한 방향을 가리키고 있었다

방향을 새로 발명한 게 아니다. 코드에 이미 깔려 있던 복선을 읽은 것에 가깝다.

- `docker-compose.yml`의 Redis 주석: *"**Redisson 클라이언트와 호환**"* — Redisson은 자바 진영의 **분산 락** 라이브러리다. 단순 캐시가 목적이었다면 나올 이름이 아니다.
- `AbstractIntegrationTest` 주석: *"**Week 3 동시성 테스트**는 `ExecutorService`로 서비스를 직접 호출하므로 MockMvc 불필요"* — 동시성 테스트를 이미 염두에 두고 베이스 클래스를 얇게 설계해뒀다.
- `BaseInitData`의 시드 재고가 하필 **100 / 50 / 3** — 마지막 메뉴만 3개다. **동시 주문 경쟁을 재현하기 딱 좋은 값**이다.
- `.github/workflows/ci.yml` 주석: *"CD는 이 워크플로 범위 밖이다. AWS 인프라가 준비되는 **Week 4**에 별도 구성."*

즉 **"Stock 엔티티 → 재고 차감 → 동시성 깨짐 재현 → 락으로 해결"** 이라는 시나리오의 1단계까지 와 있는 상태다. 이 기획은 그 나머지를 잇는다.

## 2. 세 개의 화면

| 화면 | 경로 | 쓰는 사람 | 하는 일 |
| --- | --- | --- | --- |
| **키오스크** | `/` | 손님 | 메뉴 고르고 주문 → **대기번호** 받고 끝. 로그인 없음. |
| **주방(POS)** | `/kitchen` | 바리스타 | 들어온 주문을 `제조중 → 준비완료`로 넘김 |

**지금은 이 셋이 전부 `/` 한 페이지에 섞여 있다.** 손님이 보는 상품 목록에 **메뉴 삭제 버튼이 그대로 노출**돼 있고, 삭제 권한 확인은 `window.prompt("삭제 권한 확인을 위해 이메일을 입력해주세요")`다. 화면 분리는 UI 정리가 아니라 **권한 경계를 만드는 일**이다.

## 4. 로드맵 — 왜 이 순서인가

각 Phase는 **"이게 없으면 다음이 성립하지 않는다"** 순서로 배열했다. 건너뛰지 않는다. 아래는 **왜 이 순서인가**만 담는다 — 각 Phase의 **구체 작업·완료기준·현재 진행 상태**는 [`docs/ROADMAP.md`](ROADMAP.md)에 있다.

---

### Phase 0 — 정체성 정리 + 결함 청산

새 기능을 얹기 전에, 지금 코드가 **두 제품 사이에서 어느 쪽도 아닌 상태**를 끝내야 한다. 특히 가격 스냅샷 부재는 시간이 갈수록 고치기 어려워진다 — 주문 데이터가 쌓인 뒤엔 소급 마이그레이션이 필요해진다.

### Phase 1 — 키오스크 루프 완성 *(제품이 처음으로 "돌아간다")*

주방 화면이 없으면 상태머신은 **아무도 호출하지 않는 코드**다. 재고(Phase 2)도 화면에서 품절이 보여야 의미가 있다. 여기서 제품이 처음으로 **끝에서 끝까지** 이어진다. 그리고 화면을 셋으로 나누는 일은 UI 정리가 아니라 **권한 경계를 만드는 일**이라, 이 단계에서 Spring Security가 함께 들어간다 (손님은 익명, 점주/바리스타는 인증 — 키오스크에서 손님에게 로그인을 요구하는 건 제품 실패다).

### Phase 2 — 재고를 주문에 연결 *(Stock이 살아난다)*

Phase 3(동시성)의 **무대를 세우는 단계**다. 재고 차감이 없으면 깨뜨릴 것도 없다. 재고 감소 로직은 서비스가 아니라 **엔티티(`Stock`)가 소유한다** — 상태 전이를 `Order`가 소유하는 것과 같은 원칙이다(§6).

### Phase 3 — 동시성 ★ 이 프로젝트의 클라이맥스

여기가 목적지다. 앞의 모든 Phase는 이 무대를 세우기 위한 것이었다. 학습 순서 자체가 설계됐다 — **먼저 깨지는 걸 눈으로 증명하고**(해결책부터 배우지 않는다), 그다음 비관적 락 → 낙관적 락 → Redisson 분산 락으로 넘어가며 **어느 쪽이 언제 유리한지를 말이 아니라 테스트로 확인한다.** Redisson까지 가야 `docker-compose.yml`의 Redis가 비로소 쓰인다.

### Phase 4 — 배포

스키마가 안정된 뒤에 마이그레이션을 도입해야 의미가 있다. Phase 0~3에서 엔티티가 계속 바뀌므로 `ddl-auto: create`는 그때까진 오히려 편하다 — 그래서 Flyway 도입을 **맨 뒤로** 미뤘다. 스키마가 "버려도 되는 것"에서 자산으로 바뀌는 지점이다.

## 5. 스코프 아웃 — 의도적으로 안 하는 것

**안 하는 이유를 남기는 것도 기획이다.** 나중에 "왜 이건 없지?"라는 질문에 답하기 위해.

| 안 하는 것 | 이유 |
| --- | --- |
| **실결제(PG) 연동** | 이 프로젝트의 주제는 **동시성**이지 결제가 아니다. PG 연동은 가맹점 심사·콜백·정산 등 **곁가지 복잡도만 크고 배울 게 적다.** 대신 "결제 완료 처리"를 모킹하고, `OrderStatus.CONFIRMED`를 "결제까지 끝난 상태"로 정의한다. |
| **회원가입 / 마이페이지** | 매장 키오스크에 회원 개념은 **제품적으로 틀렸다.** 손님은 익명이어야 한다. `Customer`는 회원이 아니라 **익명 주문 주체**로 축소한다. |
| **WebSocket 실시간 푸시** | 주방 화면은 **폴링 3초로 충분하다.** 카페 주문은 초당 수십 건이 아니다. 동시성(Phase 3)이 끝난 뒤 여유가 있으면 그때 한다. |
| **다국어(i18n)** | 실제 키오스크엔 필요하지만 학습 주제와 무관. |

## 6. 도메인 모델 목표 상태

Phase 0~2에서 바뀌는 부분만.

```
Order
  - address, postcode          ← 제거 (배송 잔재)
  + orderNumber : String       ← 대기번호
  + totalPrice  : int          ← 주문 시점 총액
    status      : OrderStatus  (유지 — 상태 전이는 엔티티가 소유)

OrderItem
  + orderPrice : int           ← 주문 시점 가격 스냅샷 (메뉴 가격 변경과 무관해진다)

Stock
  + decrease(int)              ← 재고 부족 시 OutOfStockException
  + increase(int)              ← 주문 취소 시 복구
  + version : Long             ← Phase 3, 낙관적 락 실험 시
```

**설계 원칙**: **상태 전이와 재고 증감은 서비스가 아니라 엔티티가 소유한다.**
`Order.startPreparing()`이 그런 것처럼 `Stock.decrease()`도 스스로 규칙을 지킨다. 서비스는 엔티티를 조회해서 메서드를 호출하기만 한다. (이 원칙은 이미 `Backend/App/CLAUDE.md`에 명시돼 있다 — 확장하는 것이다)
