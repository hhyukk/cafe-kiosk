# ADR-0006. 점주 토큰은 이 서버가 HS256 으로 발급하고 Spring Security 리소스 서버로 검증한다

- 날짜 2026-11-17
- 상태 채택됨
- 근거 문서 `docs/REQUIREMENTS.md` FR-AUTH-01 부터 10 과 NFR-SEC-01, 04, 05, 06, `docs/API.md` 2-3 과 4-1, `docs/ERD.md` 3-1

## 맥락

점주 API 가 전부 열려 있었다. 권한 경계라고 부를 만한 것은 메뉴 수정과 삭제가 요청 본문의 이메일을 등록자와 비교하는 것 하나였고, 주문 목록과 상태 변경과 재고 조정과 이미지 업로드는 누구나 부를 수 있었다.

요구사항은 이미 많은 것을 정해 두었다. 인증은 stateless JWT 이고 서명은 HS256 이며 키는 32바이트 이상이다. 비밀번호는 해시로만 저장한다. 점주 API 를 토큰 없이 부르면 401 이다. 토큰은 BFF 가 httpOnly 쿠키로 보관하고 로그아웃은 BFF 가 쿠키를 지우는 것으로 성립한다. 리프레시 토큰은 두지 않는다.

정하지 않은 것이 넷이었다. 무엇으로 토큰을 만들고 검증하는가. 로그인 응답의 어디에 토큰을 싣는가. 로그아웃이 백엔드에 자리를 갖는가. 경로별 권한을 무엇을 기본으로 적는가.

## 결정

**1. 검증은 Spring Security 리소스 서버가 하고 발급은 `NimbusJwtEncoder` 가 한다.** `spring-boot-starter-security-oauth2-resource-server` 를 들인다. Authorization 헤더에서 Bearer 토큰을 꺼내 서명과 만료를 검증하는 일은 `BearerTokenAuthenticationFilter` 와 `NimbusJwtDecoder` 가 한다. Spring Security 는 토큰을 찍는 엔드포인트를 주지 않으므로 발급은 `AccessTokenIssuer` 가 `NimbusJwtEncoder` 로 한다. 이름에 OAuth2 가 들어 있지만 인가 서버는 없다. 리소스 서버 지원은 직접 만든 JWT 에도 쓸 수 있다고 공식 문서가 적고 있다.

서명은 HS256 하나로 못 박는다. 발급과 검증이 같은 서버라 비밀키 하나면 충분하고, 디코더는 헤더의 alg 가 무엇을 주장하든 이 키로 만든 HS256 서명만 받는다. 키는 base64 로 적은 32바이트 이상의 난수이고 환경 변수에서만 읽는다. 짧으면 `JwtConfig` 가 기동을 멈춘다.

토큰의 sub 는 점주 이메일, role 클레임은 `ROLE_OWNER`, 수명은 12시간이다. 리프레시 토큰이 없으므로 수명이 곧 다시 로그인하는 주기이고, 영업 하루를 로그인 한 번으로 버티게 잡았다. sub 를 이메일로 둔 것은 메뉴 등록자처럼 서버가 검증한 신원이 필요한 자리에서 `Authentication.getName()` 이 곧 이메일이 되게 하려는 것이다.

**2. 로그인 응답은 본문에 토큰을 싣는다.** `RsData` 의 data 에 `accessToken`, `email`, `role` 을 담는다. 응답을 받는 것은 BFF 이고, BFF 가 토큰을 꺼내 httpOnly 쿠키로 심은 뒤 나머지만 브라우저로 넘긴다.

로그인 실패는 이메일이 없는 경우와 비밀번호가 틀린 경우가 같은 401 이다. 메시지뿐 아니라 걸리는 시간도 맞춘다. 없는 이메일에도 미리 만든 해시와 비교를 한 번 치른다. 판정은 `AuthService` 가 직접 하고 실패는 `InvalidCredentialsException` 하나로 던진다.

비밀번호 해시는 `Owner` 생성자가 만든다. 생성자는 평문과 `PasswordEncoder` 를 받고, 해시를 받는 생성자는 없다. 인코더는 `BCryptPasswordEncoder` 다.

**3. 로그아웃은 BFF 가 쿠키를 지우는 것이고 백엔드에는 엔드포인트가 없다.** 토큰이 stateless 라 서버에는 지울 상태가 없다. `docs/API.md` 3절 표에서 로그아웃 행을 걷어냈다.

**4. 경로 표는 잠긴 것이 기본이다.** `global/security/SecurityConfig` 가 손님에게 여는 경로만 공개 목록에 적고 나머지는 전부 `hasRole("OWNER")` 다. 공개 목록은 로그인, 메뉴 목록 조회, 주문 생성, 이메일로 하는 주문 내역 조회, `/uploads/**`, Swagger, 그리고 컨테이너 안의 ERROR 디스패치다. 메서드까지 맞춘다.

401 은 `RsData` 봉투로 나간다. 보안 필터에서 터진 예외는 DispatcherServlet 을 거치지 않으므로 `RsDataAuthenticationEntryPoint` 가 MVC 의 예외 리졸버로 넘겨 `GlobalExceptionHandler` 가 봉투를 쓴다. 상태와 `WWW-Authenticate` 헤더는 프레임워크의 `BearerTokenAuthenticationEntryPoint` 가 먼저 쓴다. 진입점은 토큰이 없을 때 쓰이는 자리와 토큰이 깨졌을 때 쓰이는 자리 양쪽에 건다.

## 버린 대안

**jjwt 와 직접 쓴 필터.** `OncePerRequestFilter` 를 짜서 헤더를 읽고 서명과 만료를 검증해 보안 컨텍스트를 채우는 방식이다. 필터 체인을 손으로 익히기에는 좋다. 버린 이유는 둘이다. jjwt 는 Spring Boot BOM 밖이라 Redisson 처럼 버전을 직접 박아야 한다. 그리고 그 필터가 하는 일을 리소스 서버가 이미 하므로, 헤더 파싱과 오류 응답을 손으로 다시 짜게 된다.

**`DaoAuthenticationProvider` 로 로그인한다.** `UserDetailsService` 를 두면 없는 이메일에 대한 시간 맞추기까지 프레임워크가 해 준다. 버린 이유는 예외다. 그 경로에서는 DB 장애도 `InternalAuthenticationServiceException` 으로 감싸여 `AuthenticationException` 계열로 나온다. 보안 필터의 인증 실패를 401 로 옮기는 핸들러가 그 계열을 받으므로 장애가 500 이 아니라 로그인이 필요하다는 401 로 둔갑한다. 시간 맞추기는 직접 해도 몇 줄이다.

**`DelegatingPasswordEncoder`.** 해시 앞에 `{bcrypt}` 같은 알고리즘 표시를 붙여 나중에 알고리즘을 갈아 끼울 길을 연다. 알고리즘이 하나뿐인 지금은 얻는 것이 없고, `docs/ERD.md` 가 password 컬럼을 BCrypt 해시 60자 기준으로 설명한 것과도 어긋난다. 컬럼 길이는 255 로 두었으므로 그날이 오면 스키마를 건드리지 않고 바꿀 수 있다.

**200 만 돌려주는 로그아웃 엔드포인트.** `docs/API.md` 3절 표에 있던 계약을 그대로 지킨다. 그런데 서버가 하는 일이 없는데 토큰이 폐기된 것처럼 보이게 한다. 점주 전용으로 두면 만료된 토큰을 든 채 누른 로그아웃이 401 로 실패하는 일까지 생긴다. 토큰을 정말 폐기하려면 서버가 폐기 목록을 들고 있어야 하고, 그 순간 stateless 가 아니게 된다.

**토큰을 응답 헤더에 싣는다.** 본문의 data 가 `docs/API.md` 의 예시와 글자 그대로 같아진다. 그러나 OAuth2 토큰 응답은 본문에 싣는 것이 관례이고, 필드로 두면 타입과 Swagger 스키마가 남는다. 응답을 받는 것은 어차피 BFF 라 브라우저에 새는 것은 없다.

**잠글 경로를 적는다.** 점주 경로를 하나씩 적으면 표가 `docs/API.md` 의 ROLE_OWNER 행과 한 줄씩 맞아 읽기 쉽다. 그러나 새 엔드포인트를 만들고 표를 잊으면 아무 일도 일어나지 않고 열린 채로 배포된다. 잠긴 것이 기본이면 같은 실수가 401 로 곧바로 드러난다.

**진입점에서 JSON 을 직접 쓴다.** 리졸버에 기대지 않아 단순하다. 대신 예외에서 HTTP 로의 매핑이 `GlobalExceptionHandler` 밖에 하나 더 생기고, 봉투가 바뀌는 날 한쪽만 바뀐다.

**테스트에서 `@WithMockUser` 를 쓴다.** 한 줄로 끝난다. 그러나 보안 컨텍스트를 미리 채우는 흉내라 서명과 만료 검증을 건너뛰고, 붙인 메서드 전체가 인증된 상태가 되어 같은 테스트 안의 손님 API 호출까지 인증된 채 지나간다. 실제로 발급한 토큰을 점주 API 요청에만 싣는 `support/OwnerToken` 을 택했다.

## 결과

**얻은 것.** 점주 API 를 토큰 없이 부르면 401 이다. 검증 필터와 디코더를 손으로 짜지 않았고 새 의존성은 전부 BOM 이 관리한다. 경로별 권한이 한 파일에 있고, 그 표가 `docs/API.md` 3절과 어긋나면 테스트가 잡는다. 서명 키는 커밋된 파일 어디에도 없다. 테스트 키도 JVM 마다 난수로 만든다.

**감수하는 것.** 로그아웃해도 토큰은 만료까지 유효하다. 쿠키가 지워질 뿐 이미 복사된 토큰을 서버가 막을 방법이 없다. 수명을 12시간으로 잡은 것이 그 창의 크기다. 계정을 지워도 마찬가지다. 토큰 검증이 DB 를 다시 읽지 않기 때문이다.

BFF 가 토큰을 쿠키로 다루기 전까지 지금 화면의 메뉴 등록, 수정, 삭제, 이미지 업로드는 401 을 받는다. 그동안 메뉴 관리는 Swagger 의 Authorize 에 토큰을 넣고 한다.

메뉴 수정과 삭제의 401 이 두 곳에서 나온다. 토큰이 없으면 보안 필터가 봉투 있는 401 을, 토큰은 맞는데 본문 이메일이 등록자와 다르면 컨트롤러가 봉투 없는 401 을 낸다. 본문 이메일 비교를 걷어내면 뒤엣것이 사라진다.

Spring Security 의 기본 헤더가 `/uploads/**` 이미지 응답에도 캐시 금지를 붙인다. 이미지가 몇 장이라 감수한다.

**방지선.** `SecurityConfigTest` 가 점주 API 일곱 개를 토큰 없이 불러 401 과 `401-1` 과 `WWW-Authenticate` 를 확인하고, 다른 키로 서명한 토큰과 만료된 토큰의 401, 손님 경로와 Swagger 의 200 을 고정한다. `AuthControllerTest` 가 로그인으로 받은 토큰이 점주 API 를 연다는 것과, 틀린 비밀번호와 없는 이메일의 응답 본문이 글자 하나까지 같다는 것을 고정한다. `OwnerTest` 가 저장되는 비밀번호가 원문이 아닌 60자 BCrypt 해시라는 것을 고정한다.
