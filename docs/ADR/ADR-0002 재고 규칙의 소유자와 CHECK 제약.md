# ADR-0002. 재고 증감 규칙을 Stock 엔티티가 소유하고 CHECK 제약을 두 번째 겹으로 둔다

## 맥락

`Stock` 은 필드 둘과 생성자만 가진 껍데기였다. 테이블도 있고 시드도 심기지만 `OrderService` 가 이 엔티티를 참조하지 않아, 재고가 0 이어도 주문이 무한히 성립했다. 깎을 무대는 서 있고 깎는 코드만 비어 있는 상태다.

다음 단계에서 주문이 재고를 깎기 시작하면 두 가지를 정해야 한다.

**부족 판단을 어디가 하는가.** 이 레포의 목적지는 재고 동시성이고, 비관적 락과 낙관적 락과 분산 락 세 전략을 같은 스키마 위에서 갈아 끼우며 비교한다. 판단이 서비스에 있으면 `if (stock.getQuantity() < count)` 가 전략마다 복사되고, 락을 바꾸는 작업이 부족 판단을 다시 쓰는 작업과 섞인다. `Order` 가 상태 전이를 소유하는 것과 같은 문제다.

**엔티티만 믿을 수 있는가.** FR-STK-06 은 어떤 경로로도 재고가 음수가 되지 않는다고 적었다. 그런데 엔티티를 거치지 않는 경로는 언제나 생긴다. 벌크 UPDATE, 네이티브 SQL, 운영자의 직접 조작이 그렇다. 그리고 락이 새는 순간이야말로 이 프로젝트가 드러내려는 것인데, 재고가 음수인 행이 조용히 남으면 테스트가 성공 건수만 세다가 통과해 버린다.

## 결정

**1. 증감 규칙은 `Stock` 이 소유한다.** `decrease` 와 `increase` 를 엔티티에 두고 서비스는 조회해서 부르기만 한다. 부족 판단은 엔티티 안에서 끝난다. 락 전략이 바뀌어도 이 메서드는 바뀌지 않는다.

**2. 부족하면 예외를 던지고 수량을 건드리지 않는다.** `OutOfStockException` 이다. 부분 차감이 남으면 주문 전체를 실패시키는 FR-STK-03 이 성립하지 않는다. 실패한 차감이 흔적을 남기지 않는 것이 상위 규칙의 전제다.

**3. 0 이하 인자는 `IllegalArgumentException` 이다.** 두 메서드가 같은 검사를 공유한다. 0 개를 깎거나 채우는 호출은 어느 경로에서도 의미가 없고, 조용히 통과시키면 호출자가 수량을 잘못 계산한 사실이 묻힌다. 더 중요한 것은 음수 차감이 곧 재고 증가라는 우회로다. `decrease(-5)` 가 통과하면 엔티티가 소유한 규칙에 구멍이 뚫린다.

**4. `stock.quantity >= 0` 과 `order_item.count > 0` 을 CHECK 제약으로 새긴다.** 엔티티가 1차 방어이고 CHECK 가 최후다. 두 겹을 두는 이유는 각자 막는 것이 다르기 때문이다. 엔티티는 정상 경로에서 의미 있는 예외를 던지고, CHECK 는 엔티티를 거치지 않은 쓰기를 막는다. 제약에 `ck_stock_quantity_non_negative` 처럼 이름을 준다. 이름이 없으면 Hibernate 가 생성한 해시가 로그에 찍혀, 락이 새는 순간 무엇이 걸렸는지 읽어내는 데 시간이 든다.

**5. Hibernate 전용 `@Check` 대신 JPA 3.2 표준 `@Table(check = @CheckConstraint(...))` 를 쓴다.** 이 프로젝트는 Spring Boot 4.0 이라 `jakarta.persistence-api` 3.2.0 과 `hibernate-core` 7.1.8 을 쓴다. 표준 어노테이션이 DDL 로 나가는 것을 실제 테이블에서 확인했다. Phase 4 에서 `ddl-auto` 를 걷어내고 Flyway 로 옮길 때 `CHECK (quantity >= 0)` 이 그대로 대응하므로 표현을 다시 해석할 일이 없다.

**6. `OutOfStockException` 은 메뉴 이름 대신 `menuId` 를 담는다.** `Stock.menu` 는 LAZY 라서 이름을 읽는 순간 프록시가 초기화되며 SELECT 가 한 번 더 나간다. 재고 부족은 동시성 테스트에서 스레드마다 터지는 경로이고, 거기에 조회를 얹으면 재려던 경쟁 구간 자체가 달라진다. `docs/ERD.md` 6절이 재고 이력 테이블을 만들지 않는 이유로 든 것과 같은 기준이다. 프록시의 식별자 접근은 초기화를 일으키지 않는다.

**7. `increase` 에 상한을 두지 않는다.** 주문 취소로 되돌리는 경우는 차감이 선행됐으므로 원래 수량을 넘지 않는다. 점주가 재고를 채우는 일은 별도 경로가 맡는다. 엔티티가 알 수 없는 값을 상한으로 삼을 방법이 없다.

**8. `OrderDto.OrderItemRequest.count` 에 `@Positive` 를, `CreateRequest.items` 에 `@Valid` 를 붙인다.** 원래 붙어 있던 `@NotNull` 은 원시 `int` 라 아무 일도 하지 않았다. `OrderController` 가 총 수량 1 개 이상 100 개 이하를 검사하지만 그것은 합계 기준이라, 5 개와 -3 개가 섞인 요청을 합계 2 로 통과시킨다. 그러면 400 이어야 할 요청이 CHECK 제약에 걸려 500 이 된다. 불변식은 스키마에 정책은 코드에 둔다는 기준을 이 자리에서 두 겹으로 세운다. `@Valid` 가 없으면 Bean Validation 이 리스트 요소 안을 들여다보지 않아 `@Positive` 가 한 번도 실행되지 않는다.

**9. `OutOfStockException` 을 409 로 내보내는 `GlobalExceptionHandler` 매핑은 이번에 넣지 않는다.** 아직 이 예외를 던지는 코드가 없다. 주문이 재고를 깎기 시작하는 단계에서 매핑과 테스트가 함께 들어간다. 지금 넣으면 어떤 요청으로도 닿지 않는 분기가 먼저 생긴다.

**10. `@Version` 을 지금 붙이지 않는다.** `docs/ERD.md` 3-4 가 낙관적 락 컬럼을 예고했지만, 붙는 순간 모든 UPDATE 에 version 조건이 따라붙는다. 락 전략을 비교하는 단계에서 그 조건이 언제부터 있었는지가 분명해야 하므로 해당 전략을 추가하는 단계로 미룬다.

## 버린 대안

**서비스가 부족을 검사한다.** `if (stock.getQuantity() < count) throw ...` 를 `OrderService` 에 둔다. 짧고 읽기 쉽다. 그런데 락 전략을 세 번 갈아 끼우는 동안 이 검사가 세 자리에 복사되고, 어느 하나에서 조건을 `<=` 로 잘못 쓰면 그 전략에서만 재고가 하나씩 새는 결함이 생긴다. 전략 비교의 결과가 락 때문인지 검사 때문인지 구분할 수 없게 된다.

**`decrease` 가 성공 여부를 boolean 으로 반환한다.** 예외 없이 흐름으로 처리하면 스택 비용이 없다. 그런데 호출자가 반환값을 무시할 수 있다. `stock.decrease(4);` 한 줄이 컴파일되고 아무 일도 없었던 것처럼 지나간다. 재고 부족은 놓치면 안 되는 사건이라 무시할 수 없는 형태여야 한다.

**부족하면 남은 만큼만 깎는다.** 재고 3 에 4 잔을 주문하면 3 잔을 판다. 매출 관점에서 그럴듯해 보이지만 FR-STK-03 이 주문 전체 실패를 요구한다. 손님이 4 잔을 받으러 왔는데 3 잔이 나오는 상황을 키오스크가 스스로 만들 이유가 없고, 여러 메뉴가 섞인 주문에서는 무엇이 몇 개 성립했는지 응답으로 설명하기도 어렵다.

**CHECK 없이 엔티티만 믿는다.** 엔티티에 검사가 있으니 중복이라는 주장이다. 그런데 이 프로젝트가 증명하려는 것이 락이 샐 때 무슨 일이 벌어지는가이고, 락이 새면 두 트랜잭션이 각자 유효한 검사를 통과한 뒤 둘 다 UPDATE 를 날린다. 엔티티 검사는 두 번 다 통과한다. 그 순간을 잡는 것은 DB 뿐이다.

**Hibernate 의 `org.hibernate.annotations.Check` 를 쓴다.** 표준이 나오기 전부터 있었고 예제도 많다. 그런데 표준이 이 버전 조합에서 실제로 동작하는 것을 확인했고, 구현 종속 어노테이션을 새로 들일 이유가 없다.

**예외 메시지에 메뉴 이름을 담는다.** 로그와 응답이 친절해진다. 그 대가로 재고가 부족할 때마다 SELECT 가 하나 붙는데, 하필 그 경로가 동시성 측정 구간이다.

## 결과

**얻은 것.** 부족 판단이 한 자리에 모였다. 앞으로 락을 세 번 갈아 끼우는 동안 `Stock.decrease` 는 바뀌지 않으므로, 전략 사이의 차이가 락 때문이라고 말할 수 있다. 그리고 엔티티를 우회한 쓰기가 실제로 거부되는 것을 확인했다. psql 로 `UPDATE stock SET quantity = -1` 을 직접 날렸을 때 `ck_stock_quantity_non_negative` 위반으로 거부됐다. Java 를 한 줄도 거치지 않은 쓰기가 막힌다는 뜻이고, 이것이 두 겹 방어의 요점이다.

**감수하는 것.** 아직 아무도 `decrease` 를 부르지 않는다. 이 단계가 끝난 시점에도 재고는 줄지 않고, 주문이 재고를 깎는 것은 다음 단계다. 규칙만 먼저 세우고 호출을 나중에 붙이는 순서라 중간 상태가 어색하지만, 반대로 하면 규칙을 정하면서 동시에 서비스 흐름을 고치게 된다.

`OutOfStockException` 이 메뉴 이름을 모르므로 로그에서 id 를 이름으로 옮기는 수고가 남는다. 손님에게 어떤 메뉴가 품절인지 알리는 것은 응답을 만드는 자리에서 결정할 일로 미뤘다.

409 매핑이 아직 없으므로, 만약 이 예외가 지금 어딘가에서 던져지면 500 이 나간다. 던지는 코드가 없어 지금은 도달할 수 없는 경로다.

`increase` 에 상한이 없어 재고를 무한히 올릴 수 있다. 점주 조정 API 가 붙을 때 그 자리에서 정책을 정한다.

**방지선.** `StockTest` 가 `OrderTest` 와 같은 결의 POJO 단위 테스트로 섰다. Spring 컨텍스트도 Testcontainers 도 없어 빠르게 돈다.

경계값을 양쪽에서 잡는다. 재고와 같은 수량을 깎으면 성공해 0 이 되고, 하나만 더 깎으면 예외다. 재고가 0 이면 1 개도 못 깎는다. 실패했을 때 수량이 그대로인지를 매번 함께 단언하는 것이 핵심이다. 예외만 확인하고 넘어가면 부분 차감이 남는 구현도 green 이 되어 FR-STK-03 을 받치지 못한다.

0 과 음수 인자도 두 메서드 모두에서 본다. 특히 `decrease(-5)` 와 `increase(-1)` 이 각각 재고를 늘리고 줄이는 우회로라 막혔는지를 고정한다.
