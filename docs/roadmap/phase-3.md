> [← 로드맵 인덱스](../ROADMAP.md), [배경과 "왜"](../PRODUCT.md)

---

## 왜 지금인가

**여기가 목적지다.** 앞의 모든 Phase는 이 무대를 세우기 위한 것이었다.

Phase 2까지 오면 "재고 3개짜리 메뉴를 4개 주문하면 거절된다"가 테스트로 통과한다. 하지만 그건 **단일 스레드 테스트**다. 스레드를 열 개로 늘리는 순간 같은 코드가 무너진다. 그 무너짐을 눈으로 보는 것이 이 Phase의 시작점이다.

**순서가 곧 학습 내용이다.** 해결책부터 배우지 않는다.

---

## 현재 코드 상태 (Phase 2 완료 시점 기준)

- `Stock.decrease(int)`가 재고 부족을 스스로 판단해 `OutOfStockException`을 던진다 → `409`
- `OrderService.createOrder`가 재고를 차감한다
- 컨트롤러의 `@Transactional`이 제거돼 트랜잭션 경계가 서비스에 있다 (Phase 2 PR #1)
- `Stock`에 `version` 필드는 **아직 없다.** 이 Phase에서 추가한다
- `build.gradle.kts`에 Redis/Redisson 의존성이 **없다**. `docker-compose.yml`의 Redis는 컨테이너만 떠 있고 아무도 안 쓴다
- `support/AbstractIntegrationTest`는 `@AutoConfigureMockMvc`를 베이스에 두지 않는다. **이 Phase를 위해 그렇게 설계됐다**(그 파일 주석에 이미 적혀 있다)

## 단계

각 단계는 PR 하나다. **순서를 바꾸지 않는다.**

| # | PR | 관측할 것 |
| --- | --- | --- |
| 1 | `test: 동시 주문에서 재고가 음수로 떨어지는 것을 증명한다` | 재고 3 / 10스레드 → **최종 재고 음수, 성공 건수 3 초과.** 이 테스트는 **실패하는 채로 커밋된다**(`@Disabled` + 사유 주석) |
| 2 | `feat: 비관적 락으로 재고 차감을 직렬화한다` | 위 테스트 통과. **락 대기로 총 소요시간이 늘어나는 것**을 측정해 기록 |
| 3 | `feat: 낙관적 락과 재시도로 재고를 차감한다` | 같은 테스트 통과. **재시도 횟수를 세서 로그로 남긴다.** 경쟁이 잦을수록 늘어난다 |
| 4 | `feat: Redisson 분산 락 도입` | 서버 2대 시나리오에서 DB 락만으로 부족한 이유. **여기서 Redis가 처음 쓰인다** |
| 5 | `docs: 세 락 전략의 트레이드오프를 실측과 함께 정리` | 1~4의 수치를 표로. 말이 아니라 숫자로 |

### 단계별 메모

**#1 깨지는 걸 먼저 증명한다**
`ExecutorService` 10스레드 + `CountDownLatch`로 동시에 출발시킨다. 재고 3개짜리 메뉴(`BaseInitData`의 "브라질 산토스"가 하필 3개다. 이 값은 우연이 아니다)에 1잔씩 10건.
락이 없으면 read-modify-write가 겹쳐 **성공 건수가 3을 넘고 재고가 음수로 떨어진다.** 그 실패를 커밋 히스토리에 남기는 게 이 PR의 목적이다.

**#2 비관적 락**
`@Lock(LockModeType.PESSIMISTIC_WRITE)` + `findByMenuIdForUpdate`. DB가 행을 잠그므로 차감이 직렬화된다. 가장 확실하지만 **대기가 생긴다.** 그 대기를 측정해서 #3과 비교할 근거로 남긴다.

**#3 낙관적 락**
`Stock`에 `@Version Long version`. 충돌 시 `ObjectOptimisticLockingFailureException`이 나고, 잡아서 재시도한다.
**재시도 루프의 위치가 이 단계의 전부다.** 아래 함정 참고.

**#4 Redisson**
서버를 2대 띄우면 DB 락은 여전히 유효하다(같은 DB를 보니까). 그래서 **왜 분산 락이 필요한가**를 정직하게 설명할 수 있는 시나리오를 골라야 한다. 예: 재고 확인과 차감 사이에 DB 밖의 작업(외부 호출, 캐시 갱신)이 끼는 경우, 또는 DB 락 경합을 애플리케이션 앞단에서 줄이려는 경우.
`build.gradle.kts`에 Redisson을 추가할 때 **사유 주석을 남긴다**(PR 템플릿 요구사항).

## 함정: 여기가 이 Phase의 진짜 가치

### ⚠️ 재고에 도달하기 전에 `Customer`에서 먼저 터진다

`OrderService.createOrder`의 첫 줄이 이렇다:

```java
Customer customer = customerRepository.findByEmail(request.email())
        .orElseGet(() -> customerRepository.save(new Customer(request.email())));
```

이건 그 자체로 read-then-write 경쟁이고, `Customer.email`은 `@Column(unique = true)`다. **동시 주문 10건을 같은 이메일로 짜면 재고가 아니라 여기서 유니크 제약 위반 500이 먼저 뜬다.** 재고 동시성을 보러 왔다가 엉뚱한 곳에서 막히는 것이다.

선택지는 셋이다. **고른 이유를 코드 주석과 #5 문서에 남긴다.**

1. 스레드마다 다른 이메일을 쓴다 (테스트만 비켜가는 것이지 버그는 남는다)
2. 고객 생성을 별도 트랜잭션(`REQUIRES_NEW`)으로 분리한다
3. 유니크 위반을 잡아 재조회한다 (upsert 패턴)

이건 실제로 **같은 종류의 경쟁 조건이 재고 말고 한 군데 더 있었다**는 발견이므로, 문서에 남길 가치가 있다.

### 재시도 루프는 트랜잭션 **밖**에 있어야 한다

낙관적 락 충돌은 **커밋 시점**에 터진다. 이미 롤백 표시가 붙은 트랜잭션 안에서 다시 시도해봐야 소용없다. 재시도는 트랜잭션이 끝난 뒤 **새 트랜잭션**에서 이뤄져야 한다.

- **같은 빈 안에서 self-invocation 하면 프록시를 안 타서** 재시도가 전부 같은 트랜잭션에서 돈다. 별도 빈으로 분리하거나 `@Retryable`을 쓴다.
- **컨트롤러에 `@Transactional`이 남아 있으면 이 구조가 아예 성립하지 않는다.** Phase 2 PR #1에서 걷어낸 게 여기서 회수된다.

### 여러 메뉴를 한 주문에 담으면 데드락이 난다

A 손님이 `메뉴1 → 메뉴2` 순으로, B 손님이 `메뉴2 → 메뉴1` 순으로 락을 잡으면 교착이다. **`menuId` 오름차순으로 정렬한 뒤 락을 건다.**

실무에서 실제로 물리는 지점이라 **별도 테스트를 쓸 가치가 있다.** 다중 메뉴 주문 2건을 서로 반대 순서로 동시에 던지는 테스트.

### 동시성 테스트에 `@Transactional`을 붙이면 안 된다

- 테스트 트랜잭션이 롤백되면서 **워커 스레드가 커밋한 내용을 검증할 수 없다**
- 애초에 스레드마다 커넥션이 달라 테스트 트랜잭션 안에 갇히지 않는다
- 뒷정리는 `@AfterEach`에서 직접 지운다

### 커넥션 풀 고갈을 락 문제로 오해하지 않는다

Hikari 기본 풀 크기는 10이다. 스레드를 그보다 많이 띄우면 **락이 아니라 커넥션을 못 얻어서** 실패한다. 테스트에서 풀 크기를 명시하고, 스레드 수와의 관계를 주석으로 남긴다.

### 테스트는 MockMvc를 거치지 않는다

`ExecutorService`로 `OrderService`를 직접 호출한다. `AbstractIntegrationTest`가 `@AutoConfigureMockMvc`를 베이스에 두지 않는 이유가 이것이다.

## 완료 기준

- [ ] 재고 3 / 동시 주문 10 → **정확히 3건 성공, 7건 409, 최종 재고 정확히 0**. 비관적, 낙관적, 분산 락 **세 전략 각각**에서 통과
- [ ] 락이 없던 버전에서 이 테스트가 **실패했다는 것**이 커밋 히스토리에 남아 있다
- [ ] 다중 메뉴 주문의 데드락 시나리오가 테스트로 있고 통과한다
- [ ] `Customer` 생성 경쟁을 어떻게 처리했는지 이유와 함께 문서에 있다
- [ ] `docker-compose.yml`의 Redis가 **처음으로 실제 사용된다**
- [ ] 세 전략의 트레이드오프가 **실측 수치와 함께** 문서에 정리돼 있다. "경쟁이 잦으면 비관적, 드물면 낙관적"을 말이 아니라 숫자로

## 여기서 하지 않는 것

| 안 하는 것 | 왜 |
| --- | --- |
| Redis 캐싱 (메뉴 조회 등) | 이 Phase의 Redis는 **분산 락** 용도다. 캐싱은 다른 주제 |
| 분산 트랜잭션 / Saga | 서비스가 하나뿐이라 무대가 없다 |
| 부하 테스트 도구 (k6, Gatling) | 여기서 필요한 건 **정확성**이지 처리량이 아니다 |
| WebSocket | Phase 1에서 미룬 것. 동시성이 끝난 뒤 여유가 있으면 |
